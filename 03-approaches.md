Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.

## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

## Ответ 1

Я бы выбрал **GitLab** как единую платформу.
- Хранение исходного кода (GitLab Git Repositories). Для каждого микросервиса можно создать свой репозиторий.
- Непрерывная интеграция (GitLab CI + собственные GitLab Runners). Позволяет при коммите автоматически запускать pipeline (сборка, тестирование, результат), на собственных агентах.
- Хранение и версионирование артефактов (GitLab Container & Package Registry). Для каждого микросервиса артефакты не смешиваются.
- Продвижение по стендам и непрерывная поставка/установка (GitLab CD). Собранный артефакт последовательно проходит через цепочку окружений, вручную или автоматически.

Соответствие требованиям:
- *Облачная система.* Можно использовать GitLab.com.
- *система контроля версий Git* В основе GitLab лежит Git.
- *репозиторий на каждый сервис* В GitLab можно создать иерархию групп и подгрупп для команд, и свой репозиторий для микросервисов.
- *запуск сборки по событию из системы контроля версий* Pipeline автоматически запускаются по событиям push, Merge Request или созданию тэга.
- *запуск сборки по кнопке с указанием параметров* Кнопка `Run Pipeline` в веб-интерфейсе позволяет вручную запустить весь пайплайн для выбранной ветки и передать входные переменные (`Variables` / `Inputs`), а директива `when: manual` позволяет запускать по кнопке отдельные шаги (например, выкладку на продакшен).
- *возможность привязать настройки к каждой сборке* Переменные окружения и конфигурация гибко привязываются к конкретной задаче, конкретному pipeline, ветке или целевому стенду.
- *возможность создания шаблонов для различных конфигураций сборок* Есть возможность создать централизованный репозиторий шаблонов и подключать их в сервисные репозитории.
- *возможность безопасного хранения секретных данных (пароли, ключи доступа)* GitLab предоставляет защищенное хранилище Masked & Protected CI/CD Variables, а также нативную бесшовную интеграцию через OIDC с внешним корпоративным хранилищем HashiCorp Vault.
- *несколько конфигураций для сборки из одного репозитория* Из одного репозитория можно запускать разные конфигурации сборок с помощью правил, а также указывать разные пути к файлу конфигурации.
- *кастомные шаги при сборке* В секциях before_script, script и after_script можно описать любые произвольные команды.
- *собственные докер-образы для сборки проектов* На уровне всего пайплайна или отдельного шага можно указывать собственные предсобранные Docker-образы.
- *возможность развернуть агентов сборки на собственных серверах* Агент GitLab Runner устанавливается на собственные физические/виртуальные серверы.
- *возможность параллельного запуска нескольких сборок* Масштабируя количество собственных серверов с GitLab Runner можно одновременно собирать десятки независимых микросервисов для разных команд.
- *возможность параллельного запуска тестов* GitLab CI позволяют разбить массив тестов на потоки и запустить их параллельно на нескольких агентах.
  
Использование GitLab закрывает весь цикл от хранения кода до выкладки в рамках единой платформы, избавляя от необходимости интегрировать и поддерживать связку из нескольких разнородных систем.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

## Ответ 2

Предлагаю использовать связку **Filebeat + Logstash + Elasticsearch + Kibana** (ELK Stack). 
- **Filebeat** — легковесный агент на каждом хосте, собирает логи приложений из stdout контейнеров
- **Logstash** - промежуточный узел, который централизованно принимает потоки от Filebeat, обрабатывает, фильтрует и преобразует записи.
- **Elasticsearch** - центральное распределенное хранилище, обеспечивающее индексацию и поиск по логам.
- **Kibana** - веб-интерфейс, запрашивает данные из Elasticsearch для визуализации

Соответствие требованиям:
- *сбор логов в центральное хранилище со всех хостов, обслуживающих систему* на каждом сервере устанавливается агент Filebeat, который собирает логи контейнеров и передает их в Logstash, а Logstash направляет обработанные записи в центральный кластер Elasticsearch
- *минимальные требования к приложениям, сбор логов из stdout*  Микросервис просто пишет сообщения в стандартный вывод stdout, а Filebeat забирает логи средствами контейнерной инфраструктуры хоста.
- *гарантированная доставка логов до центрального хранилища* Для повышения надёжности доставки Filebeat использует registry для отслеживания позиции чтения и дисковую очередь (disk queue). При передаче данных используется механизм подтверждения приёма и повторных отправок. На стороне Logstash включается Persistent Queue для временного хранения событий на диске. При временной недоступности сети или Elasticsearch накопленные записи передаются после восстановления соединения.
- *обеспечение поиска и фильтрации по записям логов* индексирует поля структурированных логов, а интерфейс Kibana предоставляет язык фильтрации KQL (Kibana Query Language) для быстрого поиска по полям, уровням ошибок и временным диапазонам.  
- *обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов* Веб-интерфейс Kibana поддерживает ролевую модель управления доступом.
- *возможность дать ссылку на сохранённый поиск по записям логов* В Kibana Discover можно настроить сложный фильтр, сохранить его как объект Saved Search и поделиться ссылкой на него.

Связка ELK является стандартом для работы со структурированными логами в микросервисах

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

## Ответ 3

Предлагаю использовать связку **Prometheus + exporters + Grafana**.

- **Prometheus** — централизованный сбор и хранение метрик, выполнение запросов и агрегация данных.
- **Node Exporter** — сбор метрик операционной системы и ресурсов каждого хоста.
- **cAdvisor** — сбор метрик потребления ресурсов контейнерами, в которых работают микросервисы.
- **Метрики приложений** — каждый микросервис предоставляет собственные метрики через HTTP endpoint, например `/metrics`.
- **Grafana** — пользовательский интерфейс для запросов, анализа и создания настраиваемых панелей мониторинга.

Соответствие требованиям:
- *сбор метрик со всех хостов, обслуживающих систему* Node Exporter и cAdvisor устанавливаются на каждом хосте, а Prometheus опрашивает их endpoints
- *сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network* Занимается Node Exporter.
- *сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network* cAdvisor собирает метрики контейнеров и при необходимости учитываются ограничения и особенности контейнерного runtime.
- *сбор метрик, специфичных для каждого сервиса* Микросервисы публикуют собственные метрики на /metrics.
- *пользовательский интерфейс с возможностью делать запросы и агрегировать информацию* Prometheus предоставляет язык запросов PromQL, Grafana отправляет запросы в Prometheus и визуализирует результаты.
- *пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы* Grafana Dashboards, панели, переменные и фильтры

Стек Prometheus + Grafana нативно адаптирован под динамическую микросервисную и контейнерную инфраструктуру
